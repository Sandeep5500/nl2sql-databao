# Silent rewrites left Spider2's BigQuery gold contradicting itself

Twelve of the 13 Spider 2.0-Lite BigQuery questions where our answer-selection judges lose have a gold label that is wrong, contradicts itself, or accepts only one of two fair readings, and none of these flaws has been publicly reported with a corrected answer. Most of the damage comes from one unannounced maintainer update (Spider 2.0-Snow on 2025-10-29, Lite on 2025-11-02) that replaced every gold result file of all 13 questions, usually with two to seven accepted variants, without touching the gold SQL. As a result, **in 6 of the 9 questions that ship gold SQL (bq045, bq397, bq151, bq308, bq002, bq424) the SQL can no longer produce any accepted answer**, and in five of them the deleted answer matches what the SQL returns. The update fixed real errors (bq424 had measured debt repayments instead of debt, bq356's count merged stations that share a placeholder ID, bq045 left out a real station) but created new ones: a scorer crash that makes four of bq389's seven files unmatchable, a name-only file that lets ga010 pass with a session count 13 times too high, an accepted 51-year sum of a debt stock in bq424, two Earth radii 1.6 parts per million apart judged with a one-centimetre tolerance in bq035, Monday-start weeks replacing the SQL's Sunday-start weeks in bq002, and patchworks of accepted formats in bq055 and bq151. bq051 and bq208 are honest two-readings questions, and only bq356's current label is sound. Correcting the labels changes which of our four candidates is right in 11 of the 13 questions: 20 of the 52 candidate answers pass today, 23 are right under strict corrections and 35 if fair alternative readings also count. Re-scoring the judges' stored verdicts under those labels recovers 1.7 to 5.6 of the 9.7 picks the deployed judge loses on these questions; the rest, mainly bq308, bq356 and bq045, are real judge errors. The only public trace is GitHub issue #151, which reported bq389's scorer crash on the day of the Lite update and has never been answered, and the one large published audit of Spider 2.0 labels checked 121 Snow tasks, none of them among these 13.

## An unannounced 2025 rewrite replaced all thirteen answer keys

Two maintainer commits deleted and replaced every gold result file for these 13 questions, with no per-question explanation: 575a7a4f ("update 1029", 2025-10-29) for Snow and 5fa8a517 ("update spider2lite eval", 2025-11-02) for Lite ([commit 575a7a4f](https://github.com/xlang-ai/Spider2/commit/575a7a4fab3515fc81e806481cd2164d05a26292); [commit 5fa8a517](https://github.com/xlang-ai/Spider2/commit/5fa8a5179c411c22ff8fd902c9e01c5bc2bf6c47)). Each commit rewrote the gold files of roughly 550 instances and raised the number of instances with more than one accepted file from 64–71 to **440**. These counts come from the git history; the maintainers publish none. For our 13 questions every old file was replaced, usually by 2–7 variants, and the scoring settings changed for 12 of them; bq389 kept its old column list.

The Lite gold SQL was left alone. bq035.sql and ga010.sql date from 2024-11-13 and the other seven from 2025-02-27, none has ever been edited, and bq051, bq055, bq208 and bq356 have no public gold SQL at all ([commit d72b6a2f](https://github.com/xlang-ai/Spider2/commit/d72b6a2f29079cd3f6abb72dc89eff3216cb5394)). The public data update log promises to record changes to "gold SQL, gold answers, and evaluation scripts", but it ends on 2025-08-06 ([data update log](https://docs.google.com/document/d/1a69mxO7m1nMndXp8H_-aggvYDbcbiS3rV9GPXEw-DeM/edit?usp=sharing)), and the README says only "We fixed the evaluation-suite issue, so scores are now more accurate and stable" ([README at 01a4c67](https://github.com/xlang-ai/Spider2/blob/01a4c67c1e3f6ab9032716b050a927abbb245f65/README.md)). Upstream, nothing in the gold files, the configs or the evaluator has changed since; the three later commits (2026-08-12) only edit the README ([compare 01a4c67...main](https://github.com/xlang-ai/Spider2/compare/01a4c67c1e3f6ab9032716b050a927abbb245f65...main)). The Lite and Snow files for all 13 questions are byte-identical, so every flaw below also affects the Snow twin (sf_bq045 and so on).

The flaws only make sense with the scorer's rules in mind. An answer passes if it matches any one accepted file. Within a file, each gold column listed in `condition_cols` (every column when the list is empty) must equal some column of the answer, compared as a whole list of values, so the row counts must agree. Numbers match within an **absolute 0.01**, `ignore_order` sorts the values before comparing, and extra answer columns are ignored ([evaluate.py](https://github.com/xlang-ai/Spider2/blob/01a4c67c1e3f6ab9032716b050a927abbb245f65/spider2-lite/evaluation_suite/evaluate.py)). The maintainers explain multiple files as "multiple correct answers due to question ambiguity or data version issues" ([#98](https://github.com/xlang-ai/Spider2/issues/98#issuecomment-2968801552)) and treat the files, not the SQL, as the label; they told one user to "use the gold result as the reference and ignore the gold SQL" ([#94](https://github.com/xlang-ai/Spider2/issues/94#issuecomment-2897676610)). No SQL was run for this report. What the gold SQL returns is inferred from its text and from equivalent queries that our candidates ran on BigQuery, which are recorded in their traces. Our candidates are the four answers our agent produced in independent sampled runs, called k1–k4.

Two patterns stand out. First, **most old answers were the gold SQL's own output**: bq397's deleted file reproduces the SQL's hit-level totals row for row under the SQL's own column names, bq002's carries the SQL's Sunday-week figure, bq151's 46.52221206 is the SQL's statistic to eight decimals, bq424's is the SQL's de-duplicated repayment series, and bq045's two names are the SQL's two stations. That origin is an inference, but it explains how a shared Lite/Snow answer key came to override BigQuery-specific behaviour.

## Six gold SQL files no longer produce any accepted answer

In these six questions the SQL and the files encode different answers. For bq045 and bq308 the files are right and the SQL is a leftover. For bq397, bq002 and bq151 both sides are defensible readings, and the files keep only one. For bq424 the SQL was wrong, and one of the new files is too lenient.

### bq397 sums a session total once per product row

The question asks, "after removing any duplicate records", for each channel with transactions from more than one country, the top country and its transaction total. `rev_transactions` stores one row per product line within each hit, and `totals_transactions` is a session-level total copied onto all of a session's rows; one sampled session spans four product rows, each carrying `totals_transactions = 1` ([k2 trace](/Users/deepikapalagani/Documents/nl2sql-databao/results/bq17/bigquery_passk_nov2026_17/lane_k2/traces/bq397.json)). The gold SQL removes only exact duplicate rows with `SELECT DISTINCT *` (such rows exist, up to ten copies of one row), then sums `totals_transactions` by channel and country, so each session's transactions are counted once per product row ([bq397.sql](https://github.com/xlang-ai/Spider2/blob/01a4c67c1e3f6ab9032716b050a927abbb245f65/spider2-lite/evaluation_suite/gold/sql/bq397.sql)). That gives **Direct 16,541, Referral 28,933, and Venezuela (447) as Social's top country**, which was the original gold.

The four current files keep one row per session instead: the United States tops every channel, Direct is **6,650–6,652** and Social is 164 ([bq397_a.csv](https://github.com/xlang-ai/Spider2/blob/01a4c67c1e3f6ab9032716b050a927abbb245f65/spider2-lite/evaluation_suite/gold/exec_result/bq397_a.csv)). The files differ from each other by 1–12 transactions because they identify sessions with different keys: keying on (visitor, visit) reproduces file b, and keying on (visitor, visit, date) reproduces file c ([k4 trace](/Users/deepikapalagani/Documents/nl2sql-databao/results/bq17/bigquery_passk_nov2026_17/lane_k4/traces/bq397.json); [k3 trace](/Users/deepikapalagani/Documents/nl2sql-databao/results/bq17/bigquery_passk_nov2026_17/lane_k3/traces/bq397.json)). Only the totals column is scored. A count per session is the meaningful number of transactions, but "removing any duplicate records" literally describes the SQL's step, so both readings are fair.

**Correct answer:** accept both readings. **Candidates:** k2 ran exactly the SQL's logic and fails today; k3 and k4 pass; k1 computed a row number but never filtered on it, so it removed nothing and is wrong under either reading.

### bq002's SQL starts weeks on Sunday, its files on Monday

All four candidates and every gold file agree that **(direct)** is the top traffic source for January–June 2017, with a best day of **$21,148.43** (2017-02-14) and a best month of **$99,301.44**. They split on the best week. The gold SQL numbers weeks with BigQuery's `EXTRACT(WEEK ...)`, where "weeks begin with Sunday" ([bq002.sql](https://github.com/xlang-ai/Spider2/blob/01a4c67c1e3f6ab9032716b050a927abbb245f65/spider2-lite/evaluation_suite/gold/sql/bq002.sql); [BigQuery date functions](https://cloud.google.com/bigquery/docs/reference/standard-sql/date_functions)). Since 2017 began on a Sunday, the peak falls in the week of Feb 12–18, worth **$35,854.64**; that was the original gold, and k4 computed it in its trace ([k4 trace](/Users/deepikapalagani/Documents/nl2sql-databao/results/bq17/bigquery_passk_nov2026_17/lane_k4/traces/bq002.json)). All three current files hold **$36,474.27**, the total for Monday Feb 13 through Sunday Feb 19 ([bq002_a.csv](https://github.com/xlang-ai/Spider2/blob/01a4c67c1e3f6ab9032716b050a927abbb245f65/spider2-lite/evaluation_suite/gold/exec_result/bq002_a.csv); [k3 trace](/Users/deepikapalagani/Documents/nl2sql-databao/results/bq17/bigquery_passk_nov2026_17/lane_k3/traces/bq002.json)), which is what Snowflake's default ISO-like, Monday-start week numbering produces ([Snowflake date and time functions](https://docs.snowflake.com/en/sql-reference/functions-date-time)).

The units are muddled too. `productRevenue` is stored as the value multiplied by 10^6 ([GA360 schema, Spider2 copy](/Users/deepikapalagani/Documents/nl2sql-databao/Spider2/spider2-lite/resource/documents/google_analytics_sample.ga_sessions.md)), so the SQL's division by 10^6 gives dollars. Two files label dollar values "MILLIONS"; the third reports true millions, and its column list scores total, daily and weekly revenue but skips the monthly figure the question asks for ([bq002_b.csv](https://github.com/xlang-ai/Spider2/blob/01a4c67c1e3f6ab9032716b050a927abbb245f65/spider2-lite/evaluation_suite/gold/exec_result/bq002_b.csv); [eval config](https://github.com/xlang-ai/Spider2/blob/01a4c67c1e3f6ab9032716b050a927abbb245f65/spider2-lite/evaluation_suite/gold/spider2lite_eval.jsonl)).

**Correct answer:** (direct); daily $21,148.43; weekly $35,854.64 with Sunday-start weeks or $36,474.27 with Monday-start weeks; monthly $99,301.44, in dollars or true millions. **Candidates:** k3 (Monday-start weeks) passes; k4 computed exactly what the gold SQL computes and fails; k1 summed only the first product of each hit and k2 divided by 10^9, so both are wrong under any reading.

### bq151's SQL counts 184 patients, its files 174 or 155

The question asks for the chi-squared statistic for KRAS and TP53 co-mutation in pancreatic adenocarcinoma (PAAD) patients, telling the solver to "incorporate clinical follow-up data" and to match patients "based on unique identifiers". The gold SQL starts from all **184** PAAD patients in the clinical table and LEFT JOINs the mutation calls, so the 10 patients with no mutation record at all count as having neither mutation. The 2×2 table is 90/27/17/50 and **χ² = 46.52**, equal to the original gold to eight decimals ([bq151.sql](https://github.com/xlang-ai/Spider2/blob/01a4c67c1e3f6ab9032716b050a927abbb245f65/spider2-lite/evaluation_suite/gold/sql/bq151.sql); [k2 trace](/Users/deepikapalagani/Documents/nl2sql-databao/results/bq17/bigquery_passk_nov2026_17/lane_k2/traces/bq151.json)).

The current files use only the **174** patients who appear in the mutation table (90/27/17/40, **χ² = 35.91**, files a and b) or an unexplained 155-patient group (χ² = 24.47, file c) ([bq151_c.csv](https://github.com/xlang-ai/Spider2/blob/01a4c67c1e3f6ab9032716b050a927abbb245f65/spider2-lite/evaluation_suite/gold/exec_result/bq151_c.csv); [k1 trace](/Users/deepikapalagani/Documents/nl2sql-databao/results/bq17/bigquery_passk_nov2026_17/lane_k1/traces/bq151.json)). Their column list is empty, so an answer must reproduce every column of a file, including frequencies or expected counts; a bare statistic, which is what the question's first sentence asks for, cannot pass any of them. The "high-quality annotations" filter (`FILTER = 'PASS'`) changes no patient's status. The 174-patient group gives the sounder statistic, because a patient with no sequencing record is missing data, not evidence of an unmutated gene. But the 184-patient reading follows the question's wording, and the sibling question bq161, built on the same SQL template, still accepts it; its gold is 90 − 50 = 40 ([bq161.sql](https://github.com/xlang-ai/Spider2/blob/01a4c67c1e3f6ab9032716b050a927abbb245f65/spider2-lite/evaluation_suite/gold/sql/bq161.sql)).

**Correct answer:** 90/27/17/40 on 174 patients, χ² ≈ 35.906, with the counts optional; 46.52 is a defensible alternative. **Candidates:** k1 (174 patients, 14 columns) passes today through file b; k2 and k4 (184 patients) are right if both patient groups count; k3 used a wrong expected-count formula (χ² = 54.29) and is wrong under any reading.

### bq424's SQL measured repayments, not debt

The question asks for the top 10 countries by total long-term external debt. The gold SQL uses indicator `DT.AMT.DLXF.CD` from the International Debt Statistics table ([bq424.sql](https://github.com/xlang-ai/Spider2/blob/01a4c67c1e3f6ab9032716b050a927abbb245f65/spider2-lite/evaluation_suite/gold/sql/bq424.sql)), which the World Bank defines as **principal repayments** on long-term external debt during a year; the amount of debt owed, the stock, is `DT.DOD.DLXF.CD` ([World Bank: DT.AMT.DLXF.CD](https://api.worldbank.org/v2/indicator/DT.AMT.DLXF.CD?format=json); [World Bank: DT.DOD.DLXF.CD](https://api.worldbank.org/v2/indicator/DT.DOD.DLXF.CD?format=json)). In this BigQuery table the stock indicator is entirely NULL (6,615 rows, none with a value), while the repayment series has 7,560 rows for 135 countries, so each country's value appears 56 times ([k4 trace](/Users/deepikapalagani/Documents/nl2sql-databao/results/bq17/bigquery_passk_nov2026_17/lane_k4/traces/bq424.json)). The SQL's `DISTINCT` therefore returns one repayment figure per country, with India first at $24.2 billion; that was the original gold.

The rewrite switched to the debt stock from the World Development Indicators tables. Files a, b and c hold the **2020 stock**, led by China at **$1.10 trillion**, followed by Brazil, India, Mexico, Russia, Indonesia, Türkiye, Argentina, Kazakhstan and South Africa. File d holds the stock **summed over 1970–2020**, led by Brazil at $9.3 trillion ([bq424_a.csv](https://github.com/xlang-ai/Spider2/blob/01a4c67c1e3f6ab9032716b050a927abbb245f65/spider2-lite/evaluation_suite/gold/exec_result/bq424_a.csv); [bq424_d.csv](https://github.com/xlang-ai/Spider2/blob/01a4c67c1e3f6ab9032716b050a927abbb245f65/spider2-lite/evaluation_suite/gold/exec_result/bq424_d.csv)). Adding up a stock across years counts the same debt again every year, so file d is a lenient patch, not a second right answer.

**Correct answer:** files a–c, the latest-year stock. **Candidates:** k1–k3 summed the stock over all years and pass only through file d; the output-shape hint shown to k1 and k3 described the target as a sum over all years ([k1 trace](/Users/deepikapalagani/Documents/nl2sql-databao/results/bq17/bigquery_passk_nov2026_17/lane_k1/traces/bq424.json)). k4 summed repayments across the 56 duplicates and fails. Under a latest-year label none of the four is right.

### bq045's SQL drops a station the question no longer excludes

The question asks for Washington stations with more than 150 rainy days in 2023 but fewer than in 2022. NOAA identifies a GSOD station by its (USAF, WBAN) pair, and hundreds of stations that have only a WBAN number share the filler USAF code 999999 ([ISD station history](https://www.ncei.noaa.gov/pub/data/noaa/isd-history.txt); [NOAA ISD problems](https://www.ncei.noaa.gov/pub/data/noaa/isd-problems.pdf)). The gold SQL joins and groups on USAF alone, so it has to exclude 999999 to avoid merging all those stations into one. That also excludes **Darrington 21 NNE** (999999-04223), a real Washington station with 167 rainy days in 2023 and 180 in 2022, and the SQL returns two stations, which was the original gold ([bq045.sql](https://github.com/xlang-ai/Spider2/blob/01a4c67c1e3f6ab9032716b050a927abbb245f65/spider2-lite/evaluation_suite/gold/sql/bq045.sql)). Grouping by USAF without the exclusion produces exactly that merged pseudo-station, with more than 365 "rainy days" ([k3 trace](/Users/deepikapalagani/Documents/nl2sql-databao/results/bq17/bigquery_passk_nov2026_17/lane_k3/traces/bq045.json)).

For about two weeks in early 2025 the question did say "excluding stations with an invalid USAF code", but the clause was removed on 2025-02-10, before the SQL was published ([commit 8208a4d8](https://github.com/xlang-ai/Spider2/commit/8208a4d8091f764f32303b75a05a3594035d2318); [commit 07c88177](https://github.com/xlang-ai/Spider2/commit/07c88177632274f26ac7d4bac925646d54ac60d4)). All four current files list three stations including Darrington ([bq045_a.csv](https://github.com/xlang-ai/Spider2/blob/01a4c67c1e3f6ab9032716b050a927abbb245f65/spider2-lite/evaluation_suite/gold/exec_result/bq045_a.csv)), so here **the files are right and the SQL is a leftover**.

**Correct answer:** Quillayute Airport, Stampass Pass FLTWO and Darrington 21 NNE. **Candidates:** k1 and k2 identify stations by USAF and WBAN and are right. k4 repeats the SQL's 999999 exclusion and k3 groups by USAF alone, so both are wrong under the current wording, though both would have passed the old label.

### bq308's SQL counts 2020 and drops unanswered questions

The question asks how many Stack Overflow questions were posted on each weekday of **2021**, and how many of them, and what share, were answered within an hour. The gold SQL has three separate faults ([bq308.sql](https://github.com/xlang-ai/Spider2/blob/01a4c67c1e3f6ab9032716b050a927abbb245f65/spider2-lite/evaluation_suite/gold/sql/bq308.sql)). It filters **2020**. Its `WHERE EXTRACT(YEAR FROM a.creation_date) = 2020` is NULL for unanswered questions, which silently turns the LEFT JOIN into an inner join and drops them from the denominator. And it rounds the percentage to one decimal, which misses the current two-decimal files by more than 0.01. The original 2024 gold already held correct 2021 counts; a May 2025 alternative that looks like the SQL's 2020 output (about 53% answered instead of 38%) was added and then deleted in the rewrite ([commit d79b85e9](https://github.com/xlang-ai/Spider2/commit/d79b85e97be4bf68f62ba1e87e77531bdb3719c6)).

The four current files agree on the question totals (Monday: 251,182) but **disagree by 0–4 on the answered-within-an-hour counts** (Monday: 94,919–94,923), and the scorer requires exact counts ([bq308_c.csv](https://github.com/xlang-ai/Spider2/blob/01a4c67c1e3f6ab9032716b050a927abbb245f65/spider2-lite/evaluation_suite/gold/exec_result/bq308_c.csv)). File d counts questions whose first answer came less than 3,600.000 seconds after the question, the exact meaning of "within one hour".

**Correct answer:** file d. **Candidates:** k3 (`TIMESTAMP_DIFF(..., MINUTE) < 60`) matches file d exactly. k2 and k4 used `TIMESTAMP_DIFF(..., SECOND) <= 3600`, which drops fractions of a second and so admits answers up to 3,600.999 seconds after the question ([BigQuery timestamp functions](https://docs.cloud.google.com/bigquery/docs/reference/standard-sql/timestamp_functions)); they count 5–12 more questions per weekday, 55 of 1.63 million in total, and fail on a one-second convention ([k2 trace](/Users/deepikapalagani/Documents/nl2sql-databao/results/bq17/bigquery_passk_nov2026_17/lane_k2/traces/bq308.json)). k1 required the answer to be strictly later than the question, so it dropped 660–1,300 questions a day whose first answer has the same timestamp, most likely self-answers posted together with the question; that is a real error.

## Scoring rules turn arbitrary conventions into pass or fail

In bq035, bq389, ga010 and bq055 the substance of the answer is settled. What fails is the scoring setup: tolerances, column lists and file formats.

### bq035 hinges on a 1.6-parts-per-million radius difference

The trips table has no distance column, so both gold files approximate each trip by the great-circle distance between its start and end stations and sum it per bike ([bq035.sql](https://github.com/xlang-ai/Spider2/blob/01a4c67c1e3f6ab9032716b050a927abbb245f65/spider2-lite/evaluation_suite/gold/sql/bq035.sql)). File b is the gold SQL's `ST_DISTANCE` output rounded to four decimals, and its column list also scores an **average distance that the question never asks for**. File a is the standard haversine formula with an Earth radius of 6,371,000 m ([bq035_a.csv](https://github.com/xlang-ai/Spider2/blob/01a4c67c1e3f6ab9032716b050a927abbb245f65/spider2-lite/evaluation_suite/gold/exec_result/bq035_a.csv); [bq035_b.csv](https://github.com/xlang-ai/Spider2/blob/01a4c67c1e3f6ab9032716b050a927abbb245f65/spider2-lite/evaluation_suite/gold/exec_result/bq035_b.csv)). For all 700 bikes, file b's total equals file a's times exactly 1 + 1.57 × 10⁻⁶, the ratio of 6,371,010 m to 6,371,000 m, so BigQuery's sphere evidently uses a radius of 6,371,010 m. Google does not document the radius, but the same figure is the R s2 package's Earth radius, while 6,371,000 m is what Snowflake's `HAVERSINE` uses ([s2 Earth radius](https://r-spatial.github.io/s2/reference/s2_earth_radius_meters.html); [Snowflake HAVERSINE](https://docs.snowflake.com/en/sql-reference/functions/haversine)).

The per-bike gaps run from **1 cm to 6.3 m, and all 700 exceed the 0.01 absolute tolerance**, so an answer must reproduce one radius to the centimetre, while bike numbers are checked in neither file. Neither radius is more correct, since station-to-station distance is only a rough stand-in for distance actually ridden.

**Correct answer:** per-bike totals with either radius. **Candidates:** k2 (haversine, 6,371,000 m) passes ([k2 trace](/Users/deepikapalagani/Documents/nl2sql-databao/results/bq17/bigquery_passk_nov2026_17/lane_k2/traces/bq035.json)). k4 used the gold SQL's own `ST_DISTANCE` call without the average column and fails both files ([k4 trace](/Users/deepikapalagani/Documents/nl2sql-databao/results/bq17/bigquery_passk_nov2026_17/lane_k4/traces/bq035.json)), although it would have passed the pre-rewrite label, which scored only bike and total. k1 and k3 cut their output with `LIMIT 20` and `LIMIT 10` and are wrong under any label.

### bq389's stale column list makes four files unmatchable

Here the SQL and the files agree. The SQL averages every row of each pollutant's daily-summary table for California in 2020, scaling SO2 by 10 and lead by 100, and its output is the original file, which even kept the SQL's mislabelled `co` header on the VOC column ([bq389.sql](https://github.com/xlang-ai/Spider2/blob/01a4c67c1e3f6ab9032716b050a927abbb245f65/spider2-lite/evaluation_suite/gold/sql/bq389.sql)). The rewrite added six more files, three wide (12 months × 7 columns) and four long (one row per month and pollutant, 3–4 columns), but **left `condition_cols` as the single list [1, 2, 3, 4, 5, 6]** ([eval config](https://github.com/xlang-ai/Spider2/blob/01a4c67c1e3f6ab9032716b050a927abbb245f65/spider2-lite/evaluation_suite/gold/spider2lite_eval.jsonl); [bq389_b.csv](https://github.com/xlang-ai/Spider2/blob/01a4c67c1e3f6ab9032716b050a927abbb245f65/spider2-lite/evaluation_suite/gold/exec_result/bq389_b.csv)). The official evaluator copies that list to every file and checks the files in order. An answer that misses file a reaches file b, where selecting columns 1–6 of a four-column table raises an IndexError, and the whole question scores 0 ([evaluate.py](https://github.com/xlang-ai/Spider2/blob/01a4c67c1e3f6ab9032716b050a927abbb245f65/spider2-lite/evaluation_suite/evaluate.py)). A long-format answer can therefore never pass. Our own copy of the scorer skips files that raise errors, but the long files still cannot match, so the outcome is the same. Separately, the VOC table mixes 106 different compounds, so their average is not a physically meaningful level, but the question names no specific compound and the literal average stands ([k3 trace](/Users/deepikapalagani/Documents/nl2sql-databao/results/bq17/bigquery_passk_nov2026_17/lane_k3/traces/bq389.json)).

**Correct answer:** the gold numbers in either layout; separate column lists per file ([3] for file b, [2] for files c, f and g) would accept the long files. **Candidates:** k1 returned exactly the gold numbers in long format and is wrongly marked wrong; k2 and k4 (wide format) pass; k3 also restricted VOC to EPA parameter 43102, total non-methane organic compounds ([EPA parameter codes](https://aqs.epa.gov/aqsweb/documents/codetables/parameters.html)), which gives values about 18 times the gold's, a defensible chemistry choice but not one the question asks for.

### ga010's name-only file passes a count 13 times too high

Every method and every gold file agrees that **Referral** had the fourth-most sessions in December 2020, and they disagree on everything else ([ga010_a.csv](https://github.com/xlang-ai/Spider2/blob/01a4c67c1e3f6ab9032716b050a927abbb245f65/spider2-lite/evaluation_suite/gold/exec_result/ga010_a.csv); [ga010_b.csv](https://github.com/xlang-ai/Spider2/blob/01a4c67c1e3f6ab9032716b050a927abbb245f65/spider2-lite/evaluation_suite/gold/exec_result/ga010_b.csv)). File a reports 23,082 sessions and file c the same plus a 17.307% share and a rank. File b is a four-row table with Referral at 23,092, whose Organic Search figure of 51,193 is exactly Organic Search plus Paid Search, although the reference document and the gold SQL both treat Paid Search as a separate channel. File d holds only the word "Referral", and the gold SQL, which returns just the channel name, reproduces only that file ([ga010.sql](https://github.com/xlang-ai/Spider2/blob/01a4c67c1e3f6ab9032716b050a927abbb245f65/spider2-lite/evaluation_suite/gold/sql/ga010.sql)). Because the column list is empty and extra answer columns are ignored, **file d passes any one-row answer that contains "Referral", whatever number sits beside it**, while a full channel ranking, a fair reading of "give me an overview", fails every file unless it copies file b's merged layout, rank column and true/false flag.

**Correct answer:** Referral, with about 23,082–23,092 sessions depending on how sessions are defined; Google's standard is to count distinct combinations of `user_pseudo_id` and `ga_session_id` ([Google Analytics developer blog](https://developers.google.com/analytics/blog/2022/hll)). **Candidates:** k1 counted 295,924 events as sessions and is the only candidate that passes today ([k1 trace](/Users/deepikapalagani/Documents/nl2sql-databao/results/bq17/bigquery_passk_nov2026_17/lane_k1/traces/ga010.json)); k2 and k3 ranked all five channels with Referral at 23,092 and fail ([k2 trace](/Users/deepikapalagani/Documents/nl2sql-databao/results/bq17/bigquery_passk_nov2026_17/lane_k2/traces/ga010.json)); k4 counted only page-view events (20,953). A label that checks the count would pass k2 and k3 and fail k1.

### bq055's six files accept some formats and reject equivalent ones

There is no gold SQL. All six files agree on the substance: **White, Asian and Black** have the largest gaps between Google's 2021 hiring shares and the BLS tech-sector averages, at **−23.25, +20.125 and +1.95 percentage points** (Google minus BLS) ([bq055_a.csv](https://github.com/xlang-ai/Spider2/blob/01a4c67c1e3f6ab9032716b050a927abbb245f65/spider2-lite/evaluation_suite/gold/exec_result/bq055_a.csv)). They differ in scale (fractions or percentage points), sign (signed or absolute) and rounding, and the column list for each file makes the set inconsistent. Running the official comparison function on equivalent answers shows that an absolute difference alone passes on the 0–1 scale but fails in percentage points, that a signed difference alone fails on both scales, and that file a's one-decimal values are matched only by one particular way of rounding ([eval config](https://github.com/xlang-ai/Spider2/blob/01a4c67c1e3f6ab9032716b050a927abbb245f65/spider2-lite/evaluation_suite/gold/spider2lite_eval.jsonl)). "Their respective differences" can fairly be reported signed or absolute, as fractions or as points.

**Correct answer:** White −23.25, Asian +20.125, Black +1.95 points, or their absolute values. **Candidates:** k1 and k3 (absolute fractions) pass; k2 (signed fractions) and k4 (signed points) fail, although all four found the same races and gaps.

## Two questions allow two fair answers, and one label is right

bq051 and bq208 have no gold SQL, and their files are consistent with each other; the question simply supports two answers and the gold accepts one. bq356's current label is correct.

### bq051 turns on which GHCN flag counts as a flag

The question asks for average daily Citibike trips in 2016 on rainy days (over 5 mm) and other days, using the nearest GHCN weather station within 50 km of lower Manhattan "that has valid, unflagged measurements". No gold SQL exists. The gold (**38,604.51 non-rainy, 36,181.38 rainy**) equals, to the last digit, the result of keeping only rows with a blank quality flag at station US1NYKN0025, which is 3.5 km away and the nearest station with any 2016 data ([bq051.csv](https://github.com/xlang-ai/Spider2/blob/01a4c67c1e3f6ab9032716b050a927abbb245f65/spider2-lite/evaluation_suite/gold/exec_result/bq051.csv); [k2 trace](/Users/deepikapalagani/Documents/nl2sql-databao/results/bq17/bigquery_passk_nov2026_17/lane_k2/traces/bq051.json)). GHCN rows carry three flags: a blank quality flag means the value "did not fail any quality assurance check", measurement flag T marks a trace of precipitation, and the source flag is filled in for every real value, so no row is literally free of flags ([GHCN-Daily readme](https://www.ncei.noaa.gov/pub/data/ghcn/daily/readme.txt)). Also dropping the trace rows, a literal reading of "unflagged", removes 12 non-rainy days and gives **38,808.61** for non-rainy days ([k1 trace](/Users/deepikapalagani/Documents/nl2sql-databao/results/bq17/bigquery_passk_nov2026_17/lane_k1/traces/bq051.json)). NOAA's definitions favour the gold's reading, but the strict reading is not unreasonable. Every reading averages over January–September only, because the trips table ends on 2016-09-30.

**Correct answer:** 38,604.51 / 36,181.38, with 38,808.61 / 36,181.38 also acceptable. **Candidates:** k2 matches the gold and k1 took the strict reading; k3 hit its step limit without an answer, and k4 counted days with no trip data as days with zero trips, so both are wrong.

### bq208 leaves out in-radius stations that recorded nothing

Six stations in NOAA's list lie within 20 miles of Chappaqua, New York, but only three have temperature data for 2011–2020: Westchester County Airport with **3,653** valid daily readings (one for every day of the decade), Danbury Municipal Airport with **3,649** and Western Long Island Sound with **1,532** ([bq208_a.csv](https://github.com/xlang-ai/Spider2/blob/01a4c67c1e3f6ab9032716b050a927abbb245f65/spider2-lite/evaluation_suite/gold/exec_result/bq208_a.csv)). The other three recorded nothing, and two of them are older IDs for the same two airports ([k3 trace](/Users/deepikapalagani/Documents/nl2sql-databao/results/bq17/bigquery_passk_nov2026_17/lane_k3/traces/bq208.json)). The gold lists only the three stations with data, so an answer that lists all six, with zeros, fails because the row counts differ. No gold SQL exists, and the two files agree. "Tell me the number of valid temperature observations they have recorded" fits the gold's reading slightly better, but listing every station in the radius is a defensible literal answer, and "observations" could even mean the hourly readings behind each daily average (87,538 for Westchester). The rewrite also changed the counts from 3,652 / 3,649 / 1,530 to 3,653 / 3,649 / 1,532 without explanation.

**Correct answer:** the three stations with those counts, or the same three plus three rows with zero. **Candidates:** k2 and k4 pass; k3 listed all six; k1 filtered on `state = 'NY'`, which drops two in-radius stations that have data, so it is wrong under either reading.

### bq356's current count is right; the old one merged stations

The question asks how many GSOD stations, with a period of record running from at least 2000-01-01 to 2019-06-30, reached 90% of the possible days with valid temperature in 2019. No gold SQL exists. Counting stations by (USAF, WBAN), the pair NOAA uses to identify them, gives **6,568**, which is current file a ([bq356_a.csv](https://github.com/xlang-ai/Spider2/blob/01a4c67c1e3f6ab9032716b050a927abbb245f65/spider2-lite/evaluation_suite/gold/exec_result/bq356_a.csv); [k4 trace](/Users/deepikapalagani/Documents/nl2sql-databao/results/bq17/bigquery_passk_nov2026_17/lane_k4/traces/bq356.json)). Counting by USAF alone merges the 1,338 station records coded 999999 into one pseudo-station with about 75,000 "days" in 2019, which gives **6,573**, the original gold. File b's 6,570 cannot be reproduced; it is not the result of a slightly different day threshold (328, 329 and 330 days give 6,575, 6,568 and 6,560), but accepting it harms no correct answer ([bq356_b.csv](https://github.com/xlang-ai/Spider2/blob/01a4c67c1e3f6ab9032716b050a927abbb245f65/spider2-lite/evaluation_suite/gold/exec_result/bq356_b.csv)).

**Correct answer:** 6,568, which only k4 returned. **Candidates:** k1 (6,573) matches the old, wrong label; k2 (6,561) dropped real stations without being asked to, and k3 (6,562) merged distinct ones.

## No public report names these errors except bq389's config

On 2026-11-18 every issue, pull request and comment in the official repository was downloaded (233 items through #234; GitHub Discussions are turned off) and searched for each question id in both its Lite and Snow form ([issues](https://github.com/xlang-ai/Spider2/issues)). Only two threads mention any of the 13. **Issue #151**, opened on 2025-11-02, the day of the Lite rewrite, reports that bq389 has "an index not given in the gold dataframe - e.g. 6 where the gold df has 4 columns"; the reporter asked for news three weeks later, and no maintainer has replied or proposed a fix ([#151](https://github.com/xlang-ai/Spider2/issues/151); [follow-up](https://github.com/xlang-ai/Spider2/issues/151#issuecomment-3567903761)). **Issue #98** asks why sf_bq002 has two gold files and drew only the "multiple correct answers" explanation ([#98](https://github.com/xlang-ai/Spider2/issues/98)). No pull request changes the gold of any of the 13, and no other thread mentions bq045, bq397, bq151, bq308, bq035, bq051, bq055, bq208, ga010, bq424 or bq356. The maintainers' last reply to any BigQuery or Snow gold report was on 2025-08-06 ([#130](https://github.com/xlang-ai/Spider2/issues/130#issuecomment-3157384675)); at least nine later reports are unanswered, and three community correction pull requests remain unmerged, including Emergence AI's Spider2-E patches and a relaxed comparator ([PR #191](https://github.com/xlang-ai/Spider2/pull/191); [PR #220](https://github.com/xlang-ai/Spider2/pull/220)). Spider2-E's evaluator patch pads column lists that are too short, but it would not fix bq389's list, which is too long.

The official record is just as thin. The data update log lists eight of the 13 (bq002, bq035, bq045, bq051, bq055, bq208, bq356, bq397) under January–May 2025 edits without saying what changed, and it has no entry for the November 2025 rewrite ([data update log](https://docs.google.com/document/d/1a69mxO7m1nMndXp8H_-aggvYDbcbiS3rV9GPXEw-DeM/edit?usp=sharing)). The project site even dates that update "2024-10-29", a year early ([spider2-sql.github.io](https://spider2-sql.github.io/)).

Published research does not cover these questions either. The largest audit, Jin, Choi, Zhu and Kang's "Pervasive Annotation Errors Break Text-to-SQL Benchmarks and Leaderboards" (PVLDB 19(5), 2026), checked the **121 Snow tasks whose gold SQL was public on 2025-08-20** and found errors in 76 of them (62.8%), counting ambiguous questions as errors ([PVLDB paper](https://www.vldb.org/pvldb/vol19/p931-jin.pdf)). None of our 13 is among them, because their Snow gold SQL has never been released, and the authors published no per-task verdicts and did not re-score Spider 2.0 ([audited SQL list](https://github.com/uiuc-kang-lab/text_to_sql_benchmarks/tree/main/SAR-Agent/spider2/sql)). They also found that the maintainers' July 2025 question rewrites cut the error rate from 66.1% to 62.8% but introduced new errors in six tasks, which parallels what the November rewrite did to these labels ([arXiv v3](https://arxiv.org/html/2601.08778v3)). Emergence AI blamed 28 of its 32 failed Snow tasks on the benchmark, mostly on changes in the underlying data, yet its patched Spider2-E keeps all 46 gold files of our 13 Snow twins byte-identical ([Emergence blog](https://www.emergence.ai/blog/spider2-under-the-microscope-data-drift-engine-gaps-and-the-case-for-spider2-e); [Spider2-E](https://github.com/EmergenceAI/Spider2-E)). Spider 2.0-AIFunc, partly written by the Spider 2.0 team, found annotation issues in 7 of 30 tasks that every strong model failed, without naming them ([AIFunc](https://arxiv.org/html/2607.06229v1)), and the original Spider 2.0 paper reports that 45% of examples had errors at the first validation and 5% after a second round ([Spider 2.0](https://arxiv.org/html/2411.07763v2)). Searches of X, Reddit and Hacker News found nothing, though those sites are poorly indexed. The corrected answers in this report are therefore new; the only correction any of these questions has received is the maintainers' own unexplained rewrite.

## Conclusion

For Spider 2.0-Lite's BigQuery questions, the released gold SQL is no longer evidence of the label. For two-thirds of these questions that have gold SQL, it returns an answer the scorer now rejects, so any audit that re-runs released SQL, as the UIUC study did for Snow, will misjudge them. What replaced it is not a single reference computation but a pile of separate implementations, several apparently run on Snowflake, and the multiple-file design that was meant to absorb ambiguity absorbs errors as well: a single lenient file (ga010's name-only file, bq424's summed file) lets wrong answers pass, and a single stale setting (bq389's column list) or arbitrary constant (bq035's radius, bq002's week start) fails right ones. Scores computed before November 2025 used a different answer key for all 13 questions, and for nearly every other task in the benchmark, so they cannot be compared with current scores.

For our judge work, these 13 questions explain less of the judges' weakness than their losses suggest, but they explain it in a useful way. Between a fifth and three-fifths of the loss here comes from the labels, depending on whether fair alternative readings count, and in four questions both judges pick exactly what the benchmark's own gold SQL returns, so their "errors" there match the annotators' original reading rather than careless judging. The real errors that remain share one pattern: the judges prefer an answer that adds a plausible restriction the question never states, or that uses a coarser identifier, such as k4's 999999 exclusion, k3's VOC code, k1's requirement that the answer come strictly after the question, and k3's station count keyed on USAF alone. That is a narrower and more testable target for prompt or training work than "BigQuery judging" in general. Because these corrections were made only where the judges lose, judge comparisons on BigQuery should be reported twice, once with the official labels and once with these questions corrected or removed. The strongest cases (per-file column lists for bq389, the lenient files in ga010 and bq424, and bq035's tolerance) are worth filing upstream, even though the maintainers have not answered a gold report since August 2025.
