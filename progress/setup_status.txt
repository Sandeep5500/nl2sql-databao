── NEW ISSUES DISCOVERED IN RUN 5 ──────────────────────────────────────────────

  ISSUE 1 — Recursion limit not preventing loops
    The recursion_limit=25 in AgentConfig maps to LangGraph recursion_limit=50 because
    LangGraph counts NODES (llm_node + tool_executor_node = 2 nodes per step).
    25 steps × 2 min/step (at 15 tok/s, 2048 max_tokens) = ~38 min for local002.
    Fix: Reduce AgentConfig recursion_limit from 25 → 12 in spider2_benchmark.py (= 24 LangGraph nodes).

  ISSUE 2 — Context overflow for E_commerce + external knowledge docs
    local003 uses RFM.md external knowledge. E_commerce schema (even compressed to table names only)
    + RFM.md + conversation history exceeds GLM's 28000 token context.
    25953 input + 2048 output = 28001 > 28000.
    Fix options:
      a) Reduce max_tokens from 2048 → 1024 for GLM (leaves 2K more room for context)
      b) Reduce max_schema_summary_length from 60K chars → 30K chars
      c) Truncate external knowledge docs more aggressively (currently at 40K chars)
    Best fix: (a) + (c) together — GLM rarely needs 2048 tokens for SQL output.

  ISSUE 3 — GLM DOES have thinking mode (progress notes were wrong)
    Tool call test confirmed GLM-4.7-Flash generates </think> tags in response content.
    Unlike Qwen3, the thinking tokens appear BEFORE the response but tool calls still work.
    The thinking overhead is small (~200-300 chars per response), manageable at max_tokens=2048.
    No action needed unless we want to save tokens (can use --override-generation-config to disable).

  ISSUE 4 — "JSON tags not found" mystery messages
    During agent execution, "JSON tags not found" is printed to stdout 5 times (one per tool call).
    Not found in any Python source file — likely from a binary/compiled component.
    Does NOT block tool calling (local004 and local007 still made tool calls successfully).
    No action needed.

── FAILURE ROOT CAUSE ANALYSIS (confirmed, 2026-04-05) ──────────────────────────

  local002 (regression + moving average):
    Symptom: Result wrong (gold ~4187.69, agent ~different)
    v1 behavior: Model hard-coded regression coefficients in the SQL literal.
    v2 behavior: With NTILE/math hint, model now queries actual sales data first
                 but still gets wrong regression or wrong moving average window.
    Root cause: Model capability — complex multi-step (regression → predict Dec dates
                → symmetric 5-day MA → sum). Likely failing at the regression step.
    DUCKDB_HINTS already contains REGR_SLOPE/REGR_INTERCEPT hint (ignored in v1).
    SQL structure: Now uses actual table data (improvement), but computes wrong answer.

  local003 (RFM segmentation):
    Symptom: 11 segments returned, gold has 9; values differ.
    Root cause: Wrong quintile scoring. Model uses linear percentage of max
                (CASE WHEN recency <= MAX*0.2 THEN 1...) instead of NTILE(5).
    v2 change: Added NTILE(5) hint to DUCKDB_HINTS. Still failing because
               the agent correctly uses customer_unique_id (fixed from v1) but
               the NTILE scoring may also need a different base date for Recency.
    In v2, trace shows agent fixed ambiguous column reference errors iteratively
    (good sign — agent is adapting). But 11 vs 9 segments means still wrong logic.

  local004 (top 3 customers by avg payment):
    Symptom: Uses customer_id (FK in orders) instead of customer_unique_id
             (requires JOIN to customers table).
    Schema is in system prompt: BOTH customer_id and customer_unique_id are visible.
    v1: Agent skipped search_context entirely, went straight to SQL.
    v2: Agent now calls search_context(retrieve_text='orders customer_id ...') ✓
        BUT still picks customer_id in final SQL — model sees both columns in
        system prompt and chooses the wrong one.
    Root cause: Model capability — question says "3 customers" (not unique), model
                uses the first customer_id it sees rather than recognizing that
                customer_unique_id is the true customer-level identifier.
    NOTE: "Use less than 50 tool calls" hint is in system prompt (tool_limit=50).
          Agent respects this (only 1-2 calls for local004). Problem is column choice.

  local007 (career span): PASS ✓. No issues.

  local008 (max games/runs/hits/HR):
    Symptom: Agent loops for 33 minutes (2023s), makes ~50-60 vLLM requests.
    Root cause: Two schema mismatches the agent can't resolve:
      1. name_given — Player table has name_given (e.g. "Peter Edward") which is
         the gold-expected column. Agent keeps using name_first || name_last
         (gives "Peter Rose" not "Peter Edward") and gets wrong results.
      2. Per-season stats — batting table has g/r/h/hr per season per player.
         Must SUM across seasons for career totals. Agent may use MAX or get
         confused by the year/stint structure.
    Correct gold SQL approach:
      SELECT 'games_played', p.name_given, SUM(b.g)
      FROM batting b JOIN player p ON b.player_id=p.player_id
      GROUP BY p.player_id, p.name_given
      ORDER BY 3 DESC LIMIT 1
      UNION ALL ... (repeat for r, h, hr)
    Fix needed: DCE enrichment for baseball may not surface name_given clearly.
    recursion_limit=100 → tool_limit=50 in system prompt. Agent ignores the
    soft limit and keeps looping. Need to reduce recursion_limit.

── HOW DCE RETRIEVAL WORKS (for reference) ──────────────────────────────────────

  Each database has chunks stored in dce.duckdb:
    - TABLE chunk: embeddable_text = "orders is a table with 14 columns. PK: orderid. FK to..."
                   display_text = YAML with full table (all columns + samples + constraints)
    - COLUMN chunk: embeddable_text = "freight is a column type REAL in orders. Not nullable. [desc]"
                    display_text = YAML with column (type + description + stats)

  Search flow:
    Agent calls search_context("customer payment total")
    → query embedded with nomic-embed-text:v1.5 (768-dim)
    → cosine similarity against all chunks in dce.duckdb
    → top-K results returned as list[{data_source_name, score, context_result}]
    → context_result = display_text YAML (table or column chunk)
    → agent reads the YAML to understand schema, then writes SQL

  The embed server (fast_embed_server.py) must be running on the same machine as
  benchmark for search_context to work (localhost:11434).
