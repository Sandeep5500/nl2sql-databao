── ALL FIXES APPLIED (as of Apr 9) ─────────────────────────────────────────────

  1. THINK-STRIPPER (spider2_benchmark.py ~line 193-320)
     Monkey-patches databao.agent.executors.llm.chat to strip <think>...</think>
     from AIMessage content before it enters history.
     GLM chat template prepends <think>, so model emits "reasoning</think>response"
     — handled by _LEADING_THINK_CLOSE_RE regex.
     Empty messages after stripping → LLM summary call (max_tokens=120, 500-char cap).
     Effect: history shrinks from ~90K chars to ~6.5K (93% reduction).

  2. PRE-SUBMIT CHECKLIST (system_prompt.jinja, 6 items after "Make sure..." section)
     1. Output shape — row count + columns match the literal question
     2. Column minimalism — only columns the question asks for
     3. Query ID selection — submit the CORRECT query_id, not the most recent one
     4. Row count sanity — "top 10" → 10 rows, etc.
     5. Filter completeness — filter on FACT table, not dimension table
     6. External knowledge compliance — verify logic matches the provided doc exactly

  3. AUTO_OUTPUT_MODALITY=FALSE (spider2_benchmark.py ~line 449)
     bao.agent(..., auto_output_modality=False)
     Disables post-submit Vega visualizer (caused httpx.ReadTimeout on local054).

  4. TRACE FIX (databao-agent/databao/agent/executors/base.py + core/thread.py)
     Problem: thread.meta() re-ran the graph after a failure, overwriting the real trace.
     Fix A (base.py _execute_stream_sync + _invoke_graph_sync):
       Wraps streaming loop in try/except, attaches last partial state to exception
       as e._partial_last_state before re-raising.
     Fix B (base.py _execute_core):
       On exception, reads e._partial_last_state and persists real failing messages
       to cache via _update_message_history() before re-raising.
     Fix C (thread.py _materialize_data):
       try/finally bumps _opas_processed_count even on failure.
       On failure, synthesizes ExecutionResult from cache so meta() never re-executes.
     Result: trace JSON files now show the actual failing run, not a re-run.

  5. RECURSION LIMITS (spider2_benchmark.py)
     agent_config = AgentConfig(recursion_limit=30, ...)   ← 30 agent steps
     executor._graph_recursion_limit = 60                  ← 60 LangGraph nodes
     (Was 16/32 → 24/48 → now 30/60)
     Why 30 not 24: local002 was 2 steps from correct at step 24.

  6. DOOM-LOOP PREVENTION (system_prompt.jinja)
     a. SET allowed: SET sqlite_all_varchar=true now explicitly permitted for
        dirty SQLite columns (previously model saw the fix in error output but
        the prompt said "Never use SET" so it couldn't apply it).
     b. DuckDB tips:
        - TRY_CAST(col AS DOUBLE) for empty-string numeric columns
        - json_extract_string(col, '$.fieldname')::DOUBLE for JSON columns
     c. Stuck-loop rule: after 3 consecutive same-kind errors, STOP and switch
        to a fundamentally different approach.

── DOOM-LOOP ROOT CAUSES (for failure analysis) ─────────────────────────────────

  Pattern A — Empty strings in numeric columns (Baseball batting: r/h/hr/g)
    Error: TypeMismatchException: expected float or integer, found "" of type "text"
    Hint in error says SET sqlite_all_varchar=true — now allowed in prompt
    Also added: TRY_CAST(col AS DOUBLE) tip in DuckDB tips section

  Pattern B — JSON coordinates column (Airlines airports table)
    Column value: {"en": "Abakan", "ru": "Абакан", "lat": 53.7, "lon": 91.7}
    Model tried string_split/array_extract/regexp_extract — all fail
    Fix in prompt: json_extract_string(col, '$.lat')::DOUBLE
    Stuck-loop rule prevents model from burning all 30 steps on this

  Pattern C — Complex multi-step query (local002: regression + moving average)
    Was 2 steps from answer at step 24 (old limit). Now limit is 30.
    "toy" = brinquedos in Portuguese — search_context cold-start timeout on step 1
    caused the model to search for "toy" (not found) for several steps.
